# AndroidBuilder repository audit

**Audit baseline:** `master` at `d06b71557a11783e1c54b3687836823fba650853` (2026-08-30). This is a remote-source audit; no local working tree was available, so local uncommitted changes cannot be assessed.

## Architecture

The repository is a flat Python application rather than a package. `romforge.py` is the CLI/TUI dispatcher and ROM build coordinator. `main.py` and `builder.py` are additional entry points. `build_pipeline.py` and `pipeline.py` provide build orchestration; `backends.py` defines execution backends; `config.py` holds Android version/build metadata; `device_resolver.py` discovers Android device/kernel/recovery repositories and detects ADB devices; `github_client.py` centralizes GitHub API access/cache; `source_manager.py` manages source checkout; `customizer.py` handles ROM customizations; `treble_port.py` generates Treble/non-Treble helper files; `tui.py` supplies interactive menus.

## Existing capabilities

- Android ROM build flow with LineageOS/AOSP source selection, repository sync, device/vendor/kernel tree cloning, selected Gerrit patch application, optional customizations, and backend execution.
- Device-tree/recovery/kernel repository search and ADB device detection.
- Android version metadata and Treble/non-Treble port-file generation.
- Local, Docker, and GitHub Actions backend options are represented in the code.

These are code-level observations, not a claim that all flows have been executed successfully in this audit.

## CLI and configuration

`romforge.py` currently dispatches `build`, `find`, `detect`, `versions`, `status`, `port`, and `clear-cache`. No `ut-check` command existed in the audited baseline. `romforge.yaml` explicitly describes itself as documentation/a starting point and says `config.py` is authoritative. `requirements.txt` says the core CLI uses the standard library and `questionary` is needed for TUI mode.

## Tests, CI, and documentation

The recursive Git tree has no `tests/`, `docs/`, `.github/workflows/`, `.gitignore`, or device-profile directory at the audited commit. `README.md` contains only a project heading and a placeholder. No automated test suite or CI workflow is present in the tree. Python version support is not declared as a formal project matrix; the source uses modern typing syntax (including `str | None`) which requires Python 3.10+ unless postponed/rewritten consistently. The project should declare and test its actual minimum Python version.

## Technical debt and risks

- Tracked `__pycache__/*.pyc` files are present; add ignore rules and remove generated bytecode in a separate reviewed change.
- The root README is effectively empty.
- There is no visible automated test or CI setup.
- Multiple orchestration/entry-point files exist; their relationship should be documented before consolidation.
- `romforge.yaml` is not loaded at runtime, per its own comments.
- The ROM build flow can invoke external tools and clone source build systems; source provenance, explicit trust boundaries, and destructive-operation safeguards deserve focused review before broader orchestration is added.
- The remote audit cannot establish local working-tree cleanliness or whether an unpushed readiness implementation exists outside the current branch.

## Readiness checker status

No `ut-check` dispatch or dedicated readiness module/profile/tests were present in the recursive tree at the audited baseline. This implementation adds a small, offline-first checker and an optional read-only GitHub repository search. It labels user input `CANDIDATE`, missing data `UNKNOWN`, and search results `CANDIDATE`; it does not infer compatibility from RAM or repository presence. Official UBports/Halium metadata matching and device-specific source validation remain incomplete.

## Relevant upstream documentation

- [UBports porting introduction](https://docs.ubports.com/en/latest/porting/introduction/index.html): porting requires device-specific hardware integration and vendor components.
- [Halium first steps](https://docs.halium.org/en/latest/porting/first-steps.html): source availability, kernel baseline, RAM/storage, and collaboration are key feasibility inputs.
- [Ubuntu Touch device directory](https://devices.ubuntu-touch.io/): use to verify existing ports; absence from a search should not alone prove impossibility.
- [UBports community ports](https://gitlab.com/ubports/community-ports): relevant community source discovery.
